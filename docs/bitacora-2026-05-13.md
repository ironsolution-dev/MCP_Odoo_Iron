**Problema**: Tras v0.3.2 con instructions directivas, ChatGPT recibía `help_response` pero NO reintentaba con JSON. Devolvía markdown al usuario "no puedo escribir".

### Fase 6 — Bug parser NL evidencia con puntos resuelto (02:00 → 02:30 UTC)

**Bug identificado en auditoría final**: `cierra tarea 150 con evidencia: Auditoria final v0.3.4 ejecutada...` falló con `evidencia demasiado corta (18 chars). Minimo 20 chars`.

**Causa**: `_EVIDENCE_RE` cortaba la captura en el primer punto literal (`\.`) del lookahead. La frase con `v0.3.4` quedó truncada a `"Auditoria final v0"` (18 chars).

- 2 regression tests nuevos cubriendo casos con puntos internos (versiones, URLs, abreviaciones).

**Deploy v0.3.5 verificado**: task:150 cerrada con `state=1_done` y evidencia completa (130+ chars con `v0.3.5` incluido).

### Fase 7 — Custom Instructions hell + purga (02:30 → 03:00 UTC)

**Problema observado**: ChatGPT de Willy disparaba "Activa el chip Odoo APL 2.0 V2 antes de continuar" de forma errática — primera invocación funcionaba, segunda fallaba en mismo chat.

**Diagnóstico iterativo**:
1. Custom Instructions con regla preemptiva → cambio a reactiva → sigue fallando.
2. Memoria de ChatGPT había guardado la frase trigger desde antes.
3. ChatGPT priorizaba la regla preemptiva memorizada sobre la reactiva en CI.
4. Conclusión: **la frase trigger misma es el problema**. Mientras exista en cualquier config, el modelo puede dispararla.

**Solución final**: purgar la frase trigger por completo.
- Memoria de ChatGPT: eliminar todas las entries que mencionen "chip", "Activa", "PROCEDIMIENTO".
- Custom Instructions Campo 1: solo bloque KAEL + **CONTEXTO ODOO informativo puro, sin reglas "si X entonces responde Y"**.
- Custom Instructions Campo 2: bloque KAEL original sin agregados.

**Hito final**: chat nuevo + GPT-5 + chip activo → Willy invocó `dame mis proyectos y tareas` → ChatGPT respondió con tabla real de proyectos + tareas + lectura ejecutiva KAEL. **Bucle definitivamente derrotado.**

## Lecciones críticas del día (preservar para futuras sesiones)

### 1. La inteligencia debe vivir server-side, no en el modelo

ChatGPT chat-mode no es confiable para seguir protocolos JSON aunque se le instruya explícitamente. Si se quiere comportamiento determinista, el servidor debe interpretar lenguaje natural y ejecutar directo. Custom Instructions complejas son frágiles.

### 2. Reglas preemptivas en Custom Instructions causan bucles

Cualquier regla del tipo `"si detecto X → responde Y"` puede disparar incluso cuando X no es real. ChatGPT puede memorizar reglas y aplicarlas erráticamente. Mejor: reglas reactivas (intentar primero, bloquear solo si runtime falla explícitamente) o pura información sin reglas de control de flujo.

### 3. Frases trigger memorizadas son persistentes

Una vez que ChatGPT memoriza una frase como respuesta condicional, persiste a través de Custom Instructions actualizadas. Purga manual de Memory es necesaria.

### 4. "Auto" en selector de modelo rompe MCP connectors

ChatGPT "Auto" puede routear a modelos que no descubren conectores. SIEMPRE seleccionar GPT-5 o Thinking explícito.

### 5. Discovery de tools se cachea por-chat en ChatGPT

Si el primer handshake de un chat falla o cachea "0 tools", ese chat queda envenenado. Abandonar y chat nuevo es la única solución.

### 6. Audit log es la única fuente de verdad

ChatGPT alucina frases técnicas como "Resource not found: search". El servidor jamás emite eso. Siempre verificar `audit.jsonl` antes de creer reportes de error del modelo.

### 7. Conectores BLUE + V2 simultáneos generan conflicto

Tener dos conectores MCP en la misma cuenta ChatGPT genera cache conflictivo. Mantener UN solo conector activo elimina ambigüedad.
